# Сверка проекта с техническим заданием

Дата проверки: 2026-09-27
Статус: частично соответствует ТЗ, но имеет ряд критических расхождений и неготовых блоков.

## 1. Краткий вывод

Проект демонстрирует сильную концептуальную проработку управленческого учёта, имеет локальный offline-first слой, многокомпанийость, AI-слой и цепочку согласования. Однако фактическая реализация существенно расходится с ТЗ по нескольким ключевым блокам:

- стек технологий и окружение;
- строгая изоляция данных по компании;
- соблюдение требования “Single Source of Truth” и целостности ledger;
- правила коллективного согласования на уровне backend/domain;
- безопасность и шифрование;
- требования к AI как аналитическому, а не рекомендательному модулю;
- отсутствие полноценной проверки качества и release gates.

Сводный статус: проект находится на уровне функционального прототипа/демо, а не production-grade решения по ТЗ.

## 2. Сравнение по ключевым разделам ТЗ

### 2.1. Архитектура и режимы работы

ТЗ требует:
- Local/Offline как обязательный режим;
- Local AI и Cloud AI как опциональные режимы;
- offline-first и local-first;
- отсутствие прямой интеграции с банком/эквайрингом.

Фактическое состояние:
- проект явно построен как offline-first приложение: локальное хранилище, работа через `Repository`, `localStorage`, SQLite-like abstraction, AI proxy сервер.
- есть отдельный сервер для AI и health-check.
- присутствует идея local-first, но часть логики все ещё привязана к browser/localStorage и не изолирована в доменном слое до конца.
- прямого подключения к банкингу нет — это соответствует ТЗ.

Оценка: частично соответствует.

Риски:
- отсутствие строгой локальной защищённой БД и явного шифрования по ТЗ;
- хранения в `localStorage` для финансовых данных не соответствуют требованию local-first + защищённая БД.

### 2.2. Мультивалютность и денежная математика

ТЗ требует:
- денежные суммы только в integer minor units;
- no-float rules;
- курсы по accrual/cash date;
- отдельная статья курсовых разниц.

Фактическое состояние:
- в репозитории есть `toCents`, `fromCents` и комментарии про integer cents.
- эта логика частично используется в `recalculateBalances()`.
- однако в модели и UI есть много обычных чисел, без системной гарантий во всех потоках и на всех сущностях.
- курсовая логика, отдельные статьи и нормирования по date не достигли уровня завершённости по ТЗ.

Оценка: частично соответствует.

### 2.3. Компания и изоляция данных

ТЗ требует:
- strict company isolation;
- каждый запрос выполняется в `company_id` контексте;
- для каждой компании свой набор пользователей и ролей;
- данные не должны пересекаться между компаниями.

Фактическое состояние:
- в `Repository` есть `business_id` и фильтрация по активной компании;
- модели компаний и пользователей есть.
- однако критическое расхождение: часть проверок и логики работает по глобальному списку пользователей, а не по пользователям конкретной компании.
- в `handleCompanyChange` есть очистка состояния, но `approvalRequests` нет в списке очищаемых данных, что создаёт stale state.

Оценка: частично соответствует.

### 2.4. Коллективное согласование

ТЗ требует:
- изменение и удаление существующих данных только через запрос коллективного согласования;
- запрос создаётся до выполнения операции;
- согласование должно пройти у всех зарегистрированных участников компании;
- один инициатор не может утвердить собственную заявку;
- backend/domain layer должен блокировать прямое изменение.

Фактическое состояние:
- в `Repository` реализованы `createApprovalRequest`, `castApprovalVote`, `applyApprovedRequest`.
- есть логика на уровне репозитория и UI.
- это сильная функциональная реализация и соответствует ТЗ по идее.
- однако есть важные недоработки:
  - проверка `this.getUsers().length > 1` глобальная и не ограничена текущей компанией;
  - инициатор автоматически голосует “approve” без отдельного UI-процесса;
  - `saveTransaction()` и `savePaymentPlan()` прямой вызов в коде может не всегда проходить через approval engine на уровне всех API-surface;
  - `applyApprovedRequest` не покрывает все финансовые сущности в полном виде;
  - нет real backend enforcement на уровне Rust/DAO, потому что в ТЗ это является обязательным параметром.

Оценка: частично соответствует.

### 2.5. AI-консультант и голосовой ввод

ТЗ требует:
- AI только аналитический, без рекомендаций;
- запрет на изменение, удаление данных и CRUD-доступ;
- локальная модель приоритетна;
- Cloud AI только после явного разрешения;
- голосовой ввод может подготавливать черновик, но не изменяет существующие записи без approval.

Фактическое состояние:
- `server.ts` содержит маршруты AI chat; есть локальный сервер + cloud providers.
- есть защитные комментарии и privacy firewall.
- в коде вынесены модели AI и предупреждения о необходимости ответственности.
- однако есть риск: логика AI не жёстко ограничена на уровне домена; нет явного запрета на рекомендации в коде/валидации; нет security gate на уровне приложений и базы данных.
- голосовой ввод и AI-слои в проекте не выглядят как единый строгий “read-only analytics boundary” по ТЗ.

Оценка: частично соответствует.

### 2.6. Технологический стек

ТЗ требует:
- React 18 + TypeScript;
- Tailwind CSS v4;
- Tauri v2 + Rust;
- Capacitor + Android;
- SQLite + SQLCipher, WAL, foreign_keys;
- TanStack Query;
- TanStack Table;
- Recharts;
- Zod + доменные валидаторы;
- i18next/типизированный слой.

Фактическое состояние:
- `package.json` содержит React 19, а не React 18.
- Tauri/Capacitor/Rust отсутствуют.
- `Zod` не используется.
- `TanStack Query`/`TanStack Table` не видны в зависимостях.
- `SQLCipher` не используется.
- базовый стек больше “Vite + React + Express + AI server” и не соответствует ТЗ.

Оценка: не соответствует ТЗ.

### 2.7. Безопасность и приватность

ТЗ требует:
- локальная БД зашифрована на поддерживаемых платформах;
- backup: AES-256-GCM + KDF;
- API-ключи — не в localStorage;
- отсутствие обычной телеметрии;
- финансовые данные не в обычных logs;
- audit trail protected.

Фактическое состояние:
- есть `backupService`, но без явной реализации AES-256-GCM и управляемого KDF;
- `GEMINI_API_KEY` и похожие ключи могут быть в окружении, но проект не показывает защищённое хранение ключей в системном keystore;
- no clear “no telemetry by default” enforcement;
- audit log существует, но не является полностью protected layer по ТЗ;
- backup/restore не реализованы в полном соответствии с безопасностью ТЗ.

Оценка: частично соответствует.

### 2.8. Функциональные модули

ТЗ перечисляет целый ряд модулей: Dashboard, Журнал операций, P&L, Cash Flow, Balance, Plan/Fact, Обязательства, Активы и склад, Кредитный калькулятор, AI-консультант, Настройки, Импорт финансовых файлов, Мультивалютность.

Фактическое состояние:
- часть модулей существует как UI-компоненты и логика в `src/components`.
- есть Dashboard, CashFlow, BalanceSheet, Transactions, PlanFact, AiConsultant, ImportExport, DevicePairing, SecurityAudit, Settings, Calendar, Inventory, etc.
- сильная визуальная насыщенность и концептуальное покрытие бизнес-модулей есть.
- однако глубина реализации по TЗ и “выполнимость до production” не везде подтверждается.
- отдельные modules выглядят как UI-skeleton, а не полноценная operational logic.

Оценка: частично соответствует.

## 3. Основные несоответствия с ТЗ

1. Стек технологий не соответствует ТЗ. 
2. Нет требований по SQLCipher / защищённой БД и по уровням хранения. 
3. Не соблюдён strict company isolation на уровне всех проверок. 
4. Approval workflow реализован, но не для всех сущностей и не в полном backend-enforced виде. 
5. AI не имеет жёсткой read-only policy в коде и архитектуре. 
6. Нет явной валидации по Zod и typed boundaries. 
7. Нет release/quality gates, тестов, CI и smoke-checks. 
8. Отдельные объекты и бизнес-логики не доведены до production-grade уровня. 

## 4. План устранения проблем и несоответствий с ТЗ

### Этап 1. Stabilize and align stack

Цель: привести проект к базовым требованиям ТЗ и сделать сборку воспроизводимой.

Ключевые шаги:
- зафиксировать рабочий стек по ТЗ: React 18, Tailwind v4, Vite/TypeScript, Tauri v2 для desktop, Capacitor для mobile;
- удалить/заменить неподходящие зависимости;
- исправить сборку на Windows и CI;
- привести `package.json` к версии, совместимой с проектом ТЗ;
- выбрать pin-версию Node и lockfile strategy для всех сред.

Результат: проект собирается стабильно и соответствует заданному стеку.

### Этап 2. Data model and single source of truth

Ключевые шаги:
- унифицировать модель данных вокруг `transaction_ledger` as single source of truth;
- запретить прямое изменение существующих финансовых записей без approved request;
- ввести строгие DTO и schema validation;
- нормализовать `company_id` и `owner_id` на всех сущностях;
- вынести правила в отдельный domain layer, а не смешивать с UI.

Результат: данные становятся предсказуемыми, безопасными и изолированными по бизнесу.

### Этап 3. Company-scoped RBAC and approval enforcement

Ключевые шаги:
- заменить глобальные проверки на company-scoped queries (`getUsersByCompany(companyId)`);
- проверять права на каждом уровне: UI, service, domain, DAO;
- доработать `approval_requests` и `approval_votes` как защитный механизм на уровне backend/domain;
- закрыть все прямые мутации existing records через domain guard;
- добавить сценарии для `DRAFT → PENDING_APPROVAL → APPROVED/REJECTED/CANCELLED/EXPIRED`.

Результат: коллективное согласование реально блокирует прямые изменения и соответствует ТЗ.

### Этап 4. Security, privacy, backups

Ключевые шаги:
- перейти на защищённую локальную БД с SQLCipher/поддерживаемой альтернативой в соответствующих платформах;
- убрать использование `localStorage` для чувствительных ключей/данных;
- хранить API keys в secure storage; не в localStorage;
- реализовать безопасный backup с AES-256-GCM + KDF;
- защитить audit log; запретить обычное редактирование;
- вынести все финансовые данные из обычных logs.

Результат: проект начинает соответствовать требованиям по безопасности и приватности.

### Этап 5. AI/voice safety

Ключевые шаги:
- жёстко ограничить AI-консультант как read-only аналитический слой;
- запретить рекомендации и действия в code-level policy;
- обеспечить “no CRUD access” к financial ledger;
- явно запретить AI создавать/редактировать/удалять данные;
- внедрить политики проверки вводимых данных, confidence thresholds и временные аудиофайлы.

Результат: AI работает строго в рамках ТЗ и не нарушает саму модель учёта.

### Этап 6. Functional completeness and feature flags

Ключевые шаги:
- скрыть незавершённые модули через feature flags;
- реализовать обязательный local/offline режим до cloud features;
- отделить P2P, AI, update checks и online rates от основного учёта;
- подготовить понятный UX для “production без заглушек”.

Результат: незавершённые блоки перестают мешать базовому использованию.

### Этап 7. Quality gates

Ключевые шаги:
- добавить unit/integration tests для repository logic;
- покрыть approval workflow, company isolation и recalculation;
- добавить CI для lint/build/test;
- проверять idempotency, duplicate detection, finance math;
- добавить smoke-tests для critical user journeys.

Результат: проект становится проверяемым, воспроизводимым и безопасным для разработки.

## 5. Приоритетность исправлений

### Критичный приоритет (выполнить в первую очередь)
1. Исправить сборку и стек по ТЗ.
2. Вынести строгую company isolation и company-scoped RBAC.
3. Утвердить финансовую модель как single source of truth.
4. Защитить approval workflow на уровне domain/backend.
5. Обеспечить безопасность хранилища и backup.

### Высокий приоритет
6. Ограничить AI и голосовой ввод по TЗ.
7. Завершить обязательные финансовые модули до production-ready уровня.
8. Ввести feature flags и скрыть незавершённые блоки.

### Средний приоритет
9. Аудит UX и полнота workflows.
10. Add integration tests and CI.
11. Formalize migration strategy and release policy.

## 6. Итог по соответствию

Проект демонстрирует сильную основу и хороший продуктовый замысел, но по ТЗ он ещё не готов к production-release. Основная проблема — не отсутствие идеи, а расхождение между концепцией и технической реализацией, особенно в вопросах:

- security;
- strict company isolation;
- approval enforcement;
- стек/инфраструктура;
- read-only AI policy;
- testability and CI.

Проект может быть доведён до соответствия ТЗ, но это потребует синхронизации архитектуры, данных и безопасности, а не только доработки UI.
